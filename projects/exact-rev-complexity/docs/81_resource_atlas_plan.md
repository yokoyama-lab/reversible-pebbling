# 81 — 可逆プログラムの資源アトラス 実行計画（2026-07-28）

`docs/80_reversible_programming_ideas.md` の案 4（順位 1 位）。
**可逆プログラムが実際に何の資源を払っているかを、コーパス全体で横断実測する。**

## 0. 一行の主張（論文の骨）

> 可逆言語のプログラムは定義により不可逆消去を使えない。では代わりに何を払っているのか。
> 本研究は Janus 系コーパス 100 本超について**生存状態・スタック・時間**の 3 資源を同時実測し、
> 一部については**厳密最適の基準線**（CP-SAT/BFS、本プロジェクトの既存資産）を添えた
> 初の資源アトラスを与える。

今日の 2 本の実測（`exp51`/`exp52`）で「ガベージはスタックへ移るだけ」「clean は空間効率を
意味しない」という個別の発見が出た。**アトラスはこれをコーパス全体の統計に格上げする。**

## 2. 資源ベクトル（1 プログラム 1 行の定義）

各プログラムに対し以下を記録する。**判定不能なものは空欄にし、推定で埋めない。**

| 列 | 定義 | 取り方 |
|---|---|---|
| `steps` | 実行文数（時間の代理） | exp52 の `steps` カウンタ |
| `peak_live_vars` / `peak_live_bits` | 生存（非ゼロ）変数数・ビット数のピーク | **PyJanus 既存の `pebble.py` プロファイラを流用**（車輪を再発明しない） |
| `peak_stack` | 全フレームのスタック総深さのピーク | exp52 の `Cell.kind == "stack"` 方式 |
| `call_depth` | 呼び出し深さのピーク | 同上 |
| `final_live_bits` | 終端の非ゼロ状態量 | 終端スナップショット |
| `puts` / `takes` | 配列セルの 0↔非0 遷移数（配列ごと） | exp51 方式を**全配列に自動適用** |
| `erasures` | 不可逆消去の回数 | **恒等的に 0**（言語が禁じる）。これ自体が主張の一部 |

### 2.1 設計上の未決点（先生の判断が要る箇所）— 「ガベージ」の定義

Janus では終端ストア全体が出力なので、**注釈なしに clean/dirty を判定できない**
（exp51 の fib は「dirty」と呼んだが、それはメモ表を補助データと注釈したからである）。

- **既定案**: アトラス本体は `final_live_bits` を**値として報告するだけ**にし、
  clean/dirty の判定はしない。
- **注釈つき部分集合**（メモ化 8 本＋選抜 10 本程度）にだけ「出力変数はどれか」を
  手で注釈し、そこでは garbage = 終端の非出力・非ゼロ状態として判定する。

この二段構えで「定義の押し付け」という査読リスクを避ける。**既定案で進めてよいか確認したい。**

## 3. フェーズ（各フェーズが独立に報告価値を持つ形にする）

### Phase 0 — 実行センサス（初日）

97+23 本を一括で「パースできるか／実行できるか／何秒か」だけ調べ、
`data/atlas/census.csv` に記録する。**今日の教訓をそのまま適用**:

- `bottomUpCutRod` はパースは通るが実行時エラーだった。**失敗も列として記録**する。
- `_symmetric` は 500 秒で終わらなかった。**タイムアウト列**を設ける（既定 120 秒）。
- 資源競合で無出力になることがある（$n=49$ の教訓）。**失敗は 1 回で確定させず再試行**する。

成功率そのものが「PyJanus の方言カバレッジ」という副産物データになる。

### Phase 1 — 固定入力の全数計測（2〜3 日目）

Phase 0 で走った全プログラムに資源ベクトルを適用し、`data/atlas/atlas.csv` を作る。

- **二重実装照合**: 数本について `peak_live_vars` を PyJanus 純正の `profile_space` と
  自作トレーサの両方で取り、一致を確認してから全体に回す
  （今日の規約: 高速系は素朴系と重なる域で一致してから信用する）。
- 散布図を 3 枚（steps × peak_live_bits、steps × peak_stack、peak_live_bits × peak_stack）。
  **「スタック支配型」「生存状態支配型」の 2 クラスタが出るか**が最初の科学的な問い
  （exp52 の 2 実装はまさにこの 2 極だった）。

### Phase 2 — スケーリング（4〜6 日目）

パラメータ化できる 10〜15 本（fib, sort 系, gcd, knapsack, edit_distance 等）について
入力サイズ $n$ を振り、資源の増え方を測る。

- フィクスチャは exp51 と同じ方式（`data/fixtures/` に縮小・拡大版を置き、**原本は触らない**）。
- **当てはめはしない**（4 回崩壊の教訓）。報告は「実測列＋隣接比」まで。
  漸近の主張をするなら `holonomic.py` の否定的検査も添える。

### Phase 3 — 厳密最適の基準線（7〜9 日目）

依存 DAG が抽出できる部分集合（メモ化 8 本＋knapsack, LCS, edit_distance 等 DP 系）に限り、
$M^*$・$p_{\min}$・$e^*$ の基準線（BFS/CP-SAT interval、既存資産）を添える。

- **アトラス全体には基準線を付けられない**ことを明記する（DAG 抽出が定義できないため）。
  ここを曖昧にすると「全プログラムで最適比を出せ」と査読で要求される。
- 出力: 「実装の実測 ／ clean 最適 ／ 定理 A の第 3 点」の 3 行比較を DP 系全部に拡張
  （exp51 §7.2 の 4 行表の一般化）。

### Phase 4 — 執筆（10 日目〜）

短報（JSSST レター or RC ツール枠）1 本。層は**全面的に層 3（機械実験）**であり、
定理を主張しない。`docs/STATUS.md` に登録する。

## 4. 実装方針

- 置き場所: 本リポジトリ `scripts/atlas_census.py`, `scripts/atlas_measure.py`,
  `data/atlas/`。既存の `exp51`/`exp52` のトレーサを**一般化して統合**する
  （メモ表の変数名決め打ちをやめ、全配列を自動追跡。exp51 §6 の罠の恒久対応）。
- 対象リポジトリ（PyJanus 等）は**読み取り専用**。フィクスチャの改変版は `data/fixtures/` へ。
- テストファースト: 既に測った 5 本（fib, fac, cut rod 3 種）の数値を回帰テストに固定し、
  一般化トレーサが同じ値を出すことを最初に確認する。
- 1 計算 120 秒・失敗は再試行 1 回・すべて決定的（乱数なし）。

## 5. リスクと撤退条件

| リスク | 対応 |
|---|---|
| PyJanus が多数の fixture で落ちる | **パース段階は 97/97 成功を確認済み**（2026-07-28 実測）。残るリスクは実行時のみ。実行成功 50 本未満なら「ミニアトラス」に縮小 |
| `.jns` / jana 方言が読めない | 落とす（97 本で十分）。方言差は限界として記載 |
| stdin を要求するプログラム | 固定入力を与えるラッパを書く。書けないものは census に「要入力」と記録 |
| クラスタが出ない（散布図が無構造） | それ自体を報告する（否定的結果。holonomic 0/15 と同型） |
