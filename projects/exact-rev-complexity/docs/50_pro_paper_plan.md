# 50 — PRO 論文の執筆計画（候補4 を主・候補1 を道具とする）

> 対象: 情報処理学会論文誌プログラミング（PRO）。ページ制限なし・加点法・研究会発表が前提。
> 詳細は `docs/40_venues.md`。

## 0. この構成の背骨は「対応定理」である

「候補4 を主・候補1 を道具」と言うとき、両者を繋ぐものが無いと**ただの2本の寄せ集め**になる。
繋ぐのは次の命題であり、**これが本論文の理論的な核**である。

> **命題（対応）**: ガベージフリーな可逆メモ化実行の系列は、メモ依存 DAG 上の
> **clean 可逆ペブリングスケジュール**と1対1に対応する。逆も成り立つ。
> したがって「峰値メモリ $p$ の下での最小実行手数」は $M^*(G,p)$ に等しい。

なぜ自然に成り立つか: **可逆プログラムはガベージを残せない**。メモ表に積んだ中間結果も
最後には消さねばならず、しかも消す操作自体が可逆でなければならない
（＝消す時点で依存先が揃っている必要がある）。これは可逆ペブリングの toggle 規則そのもの、
そして「終端で目標だけが残る」は clean 条件そのものである。

**この命題を書けば、候補1 の道具（厳密 BFS・Aut 商・スケジュール抽出・検証器）が
そのまま「可逆メモ化実装の最適性を判定する道具」になる。** 逆にこの命題を書かないと、
ペブリングの話は PRO の読者にとって他人事になる。

**執筆上の最優先事項は、この命題を（証明と実装レベルの検証の両方で）固めること。**

### 0.1 ⚠️ 既存実装を見て分かったこと（2026-07-27、計画の修正）

`~/dev/overleaf/2021_rev_memoization2/programs/` を読んだところ、
**既存実装は clean（ガベージフリー）ではない。** `topDownCutRod.janus` 等は
**ガベージスタック `g` に値を push して退避**している（`push(max,g) // zero clear max`）。
5 ファイル中 4 ファイルで `push`/`pop` を使用。しかも同ディレクトリの `memo` に
著者自身のメモが残っている:

> メモリ使用量は実行時間に比例する。max を求めるのにメモリが必要。
> **局所的に Bennett 法にすると実行時間がかかる。**

つまり**時間と峰値メモリの緊張は当時すでに認識されていて、ガベージスタック側（時間優先）を
選んでいた**。これは計画にとって悪い知らせではなく、**論文の物語がむしろ強くなる**。

**修正後の構図（3点を1つの軸に並べる）**:

| 立場 | 峰値メモリ | 時間 | 対応するモデル |
|---|---|---|---|
| ガベージスタック（既存実装の既定） | **実行時間に比例して増える** | 最小 | clean でない＝標準ペブリング側 |
| 局所 Bennett 法（`_symmetric` 版が該当） | 抑えられる | 増える | clean 可逆ペブリング |
| **本論文が出す最適スケジュール** | $p$ に抑えたうえで | **$M^*(G,p)$＝厳密最小** | clean 可逆ペブリング（最適） |

→ **論文の主張が「実装は $c$ 手損している」よりも強い形になる**:
**「既存実装は2つの極（ガベージ蓄積 vs 局所 Bennett）しか持っておらず、
その間の最適点を誰も計算していなかった。厳密最適はその中間にあり、両極より良い」。**

さらに `topDownCutRod_twoMemoTables.janus`（「2つのメモ表による効率的解法」）は、
表を分けることで再計算を避ける設計＝**ペブル本数を増やして手数を減らす**トレードオフの
実例であり、$M^*(G, p_{\min}+k)$ のトレードオフ曲線に直接対応する。**節6 の格好の題材。**

**したがって対応定理は2本立てにする必要がある**:
- 命題1: **clean な**可逆メモ化実行 ⟺ clean 可逆ペブリングスケジュール（上記の命題）
- 命題2: **ガベージスタックを持つ**実行 ⟺ 消去を許すペブリング（＝候補3 の m-erasure ゲーム、
  スタックへの退避が「不可逆消去」に相当するかを詰める）。
  → **候補3 がここで効いてくる。** 3候補が1本に繋がる。

この修正は §3（追加実験）の A の内容を変える: **まず既存実装がどちらの極にいるかを
ファイル単位で分類する**ことが最初の作業になる。

## 1. 主張の階層（加点法を意識して「突出点」を1つに絞る）

PRO の査読は「どれか一つの点で特に優れていれば採録」。**突出点を1つに決めて全体を組む。**

- **突出点（これを売る）**: 可逆メモ化の実行スケジュールが最適かという問いに、
  **厳密最適値との比較で初めて定量的に答えた**。
- 副次的貢献:
  1. 対応定理（可逆メモ化 ⟺ clean 可逆ペブリング）
  2. 厳密最適を実用的な範囲まで計算する手法（ビットマスク双方向 BFS・Aut 商探索）と、
     その**厳密性の証明**（対合性から状態グラフが無向／始点と終端が Aut 不変）
  3. **閉形式が存在しないことの証拠**（低階 P-recursive 漸化式の非存在を全数検査）
     → 「だから表と探索が必要」という論文の存在理由になる
  4. 実装への具体的な改善指針
- **弱点（隠さず、限界として書く）**: 閉形式なし／到達範囲が有限（fib 型 $n\le49$、
  grid $k\le6$）／Lean 検証は表の一部のみ／$M^*(T_7)$ 未確定（候補1側）。

## 3. 追加実験（優先順・依存関係つき）

### A. トレース抽出と対応定理の実装レベル検証 【最優先・これが無いと論文にならない】

- 対象実装を1つ確定する（→ §6 で先生に確認）。`2017_rev_memoization/program/`、
  `2021_rev_memoization2/programs/`、`rev_PE` のいずれか。
- インタプリタにメモ表イベント（entry の書き込み／読み出し／削除）のログを吐かせる。
- ログを `(put|take, ノード)` 列に正規化し、**既存の検証器 `verify_schedule` に通す**。
  通れば対応定理の実装レベルの裏付けになる。**通らなければ対応定理の仮定が甘い**ので、
  何が違うのか（読み出し回数、キー計算のコスト、永続再利用）を突き止めて定理を修正する。
- 成果物: `scripts/exp50_trace_to_schedule.py`, `tests/test_exp50_trace.py`。

### B. 既存実装と厳密最適の差の測定 【最優先・本論文の主結果】

- A で正規化したスケジュールの手数と峰値を測り、同じ峰値での $M^*$ と比較。
- 出力形式: 「$n\le N$ では最適、$n=K$ から $c$ 手（$x\%$）損」という表。
- 差の分類は先行プロジェクトの分類（部分消去の交錯・不均等セグメント・早期再配置）を流用。

### C. 最適スケジュールからの規則抽出と実装への還元 【PRO 向けの価値が最大】

- 最適解に共通する操作パターンを抽出（候補1 が見つけた「飽和直線スイープ」が有力）。
- **それを実装のスケジューラに入れて、実プログラムで効果を測る。**
  PRO の読者は「で、実装はどう良くなるのか」を見る。ここがあると採録可能性が上がる。

### D. 実プログラムのメモ DAG 【中〜高】

- 編集距離・LCS・ナップサック・行列連鎖乗算の実際のコードから依存 DAG を抽出し、
  厳密最適を計算する。**「作った DAG 族」ではなく「実際のプログラム」**であることが重要。
- 到達範囲の壁に当たるので、実用サイズと計算可能サイズのギャップを正直に議論する。

### E. Lean 二層検証 【中】

- L2: `fib_mstar_table : ∀ n ≤ 16, ...` を `native_decide`。
- L1: 対応定理の形式化（できれば）。加点法なら「形式検証済み」は強い加点要素。
- 既存資産 `gen_janus/260612/formal/GenJanus/Hard18.lean` を写して形を作る。

### F. $p_{\min}$ ブラケット倍加の追加検証（$L(11)=16$、$n=49..64$）【中〜低】

- 予想が5組目まで生き延びている唯一の例。6組目が付くと主張が強くなる。
- ただし計算が重い。時間があれば。

### G. min-plus 遷移行列化 【今後の課題として言及のみ】

- 本論文では「閉形式が無い理由」の説明に留め、実装は次の論文に回す。
