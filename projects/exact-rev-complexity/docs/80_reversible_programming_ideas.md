# 80 — 可逆プログラミング × 成熟ツール（2026-07-28）

`docs/00_overview.md` の10候補は**厳密計算量**のテーマだった。本稿は対象を
**可逆プログラミング（言語・処理系・変換）**に移し、2026 年時点で導入済みの成熟ツール
（`~/dev/CLAUDE.md` の一覧、`docs/32_tools_installed.md`）で何が狙えるかを並べる。

## 0. 選定に使った基準（今日の実測から得たもの）

1. **道具は有界な問いに効く。全称命題に届くのは Lean だけ**（`docs/70_tool_prospects.md`）。
   → 各案について「**何が層1（確定）になりうるか**」を明記する（`docs/STATUS.md` の層）。
2. **検証器がある側（上界・構成）は未成熟な道具でよい。** 出力を検証器に通せば嘘が排除できる。
   → 可逆プログラミングは**逆プログラムを走らせて恒等性を見れば検証できる**ので、
   この非対称性が極端に強い。**ここが本分野の最大の武器。**
3. **問いを決めてから道具を選ぶ。** 今日 TRS 一式を問いなしで入れて 6 個中 0 個使った。
4. **既知性は一次文献の本文で確認する。** wiki・リーダーボードも既知の所在になりうる。
5. **少数点の当てはめを結論にしない**（4 回崩壊した）。

## 1. 可逆性を項書き換え系の性質として自動判定する 【TRS 一式の唯一の使い道】

- **道具**: ACP（合流性・青戸/新潟大）、AProVE（停止性）、**CeTA**（証明書検証・Isabelle 製）
- **なぜ噛むか**: 「プログラム $P$ の逆 $P^{-1}$ も同じ言語のプログラムか」「正規形上で単射か」は
  **合流性・停止性・単射性の組合せ**で書ける。道具を作らずに済む。
- **初日の実験**: R-CORE の最小核を TPDB 形式の TRS に落とし、ACP に投げて合流性が出るか見る。
  出たら「可逆性 ⟹ 合流性」の逆が成り立つ範囲を探す。
- **層**: CeTA の証明書が付けば**層1 相当の外部認証**（ただし TRS の性質についてであり、
  言語の可逆性そのものの層1 ではない）。
- **既知性リスク**: 中。「可逆 TRS」は Morita 系の文脈で研究がある。**先に本文確認。**

## 2. 逆プログラム変換の正しさを Lean/Rocq で機械検証する 【層1 が狙える】

- **道具**: Lean 4 + Mathlib（または既存の `rcore-rocq-proofs`）
- **なぜ噛むか**: $[\![\mathcal{I}(P)]\!] = [\![P]\!]^{-1}$ は**全称命題**。今日の結論どおり
  Lean 以外に手段がない。しかも既存資産がある（`2025_SOS_RCORE` の操作的意味論、
  `rcore-rocq-proofs`）。
- **初日の実験**: R-CORE の SOS を Lean に写し、最小の構文（増減代入・スワップ・
  条件付き反転）だけで逆化の正しさを証明する。
- **層**: **層1（確定）が取れる唯一級の案。** 今日 Lean で層1 を取れたのは候補10 の
  2 定理だけだったので、ここを増やす価値は大きい。
- **既知性リスク**: 低〜中。紙の証明は既にあるが**機械検証は未着手**（形式化枠に出せる）。

## 3. 可逆コンパイラの翻訳等価性をプログラムごとに検証する

- **道具**: z3 / CP-SAT / BMC（ABC・nuXmv）
- **なぜ噛むか**: `rcc`（可逆 C コンパイラ）や Janus→C 変換の正しさは、
  **一般には Lean 案件だが、プログラムごと・有界入力なら SMT で片付く**。
  今日の教訓（有界なら道具が効く）の直接の適用。
- **初日の実験**: 小さな Janus プログラムを 1 本選び、原プログラムと生成 C の
  入出力等価性を有界入力（例: 8 ビット）で z3 に問う。
- **層**: 層3（有界検証）。**「$n\le N$ で検証」を「正しい」と書かない**規律が要る。
- **既知性リスク**: 低。translation validation は一般的手法だが可逆言語への適用は薄い。

## 4. 可逆プログラムの資源アトラス 【今日作った計測基盤がそのまま効く・最も確実】

- **道具**: 本日実装した PyJanus 計測器（`scripts/exp51_janus_trace.py`,
  `exp52_cutrod_trace.py`）＋ CP-SAT（最適基準線）
- **なぜ噛むか**: 今日 2 本のプログラムで
  **メモ空間・スタック深さ・実行歩数・消去回数**を同時に測れることを実証した。
  これをベンチマーク集合に広げれば、**可逆プログラムの資源プロファイルの初の体系的実測**になる。
  しかも各点に**厳密最適の基準線**（CP-SAT/BFS）を添えられるのは我々だけ。
- **初日の実験**: `rwhile-C-ocaml`・`PyJanus`・`janus-oracle` の examples を全部流し、
  4 資源を表にする。動かないものは正直に「未計測」と記録する。
- **層**: 層3（機械実験）。ただし**測定は測定として価値がある**（定理は要らない）。
- **既知性リスク**: **低。** 可逆プログラムの資源を横断的に実測した文献は見当たらない。

## 5. ガベージ最小化スケジューリングのコンパイラパス 【今日の理論の実装】

- **道具**: CP-SAT（retention interval 型。`scripts/cpsat_interval.py` を流用）
- **なぜ噛むか**: 今日示した「第 3 の設計点」（$\Theta(\sqrt n)$ 空間で線形時間）を
  **実際にコンパイラパスとして作る**。どこで uncompute し、どこで消去するかを CP-SAT が決める。
  上界側なので**検証器で担保できる**（生成コードを走らせて恒等性を確認）。
- **初日の実験**: `rev_PE` か cut rod のメモ DAG を入力に、CP-SAT が出したスケジュールを
  Janus のソースに落とし、PyJanus で実行して資源を実測する。**理論値と一致するか見る。**
- **層**: 層3（実装＋実測）。ただし**理論の裏付けは層2 の定理 A**。
- **既知性リスク**: 低。ML の再計算スケジューリングは既知だが**可逆言語のパスとしては無い**。

## 6. LLM 生成可逆プログラムの自己検証ベンチマーク 【非対称性が最大】

- **道具**: 既存インタプリタ（PyJanus 等）＋ 性質ベーステスト（Hypothesis）＋ LLM
- **なぜ噛むか**: **可逆プログラムは正解判定が無料**である。生成物 $P$ について
  $P^{-1}\circ P = \mathrm{id}$ を走らせれば良い。つまり
  **LLM の出力を人手評価なしで機械判定できるベンチマーク**が作れる。
  一般のコード生成ベンチマークが抱える「正解の曖昧さ」がこの分野には無い。
- **初日の実験**: `gen_janus`・`RevPython` の既存プロンプトを流用し、
  「生成 → 逆化 → 恒等性検査」を自動化して合格率を出す。
- **層**: 層3（実験）。ベンチマーク自体が成果物。
- **既知性リスク**: 中。`gen_janus`・`RevPython` が既にあるので**自分たちの続報**になる。
  差分は「**検証を自動化して人手評価を外した**」点。

## 7. 可逆言語の停止性・複雑度解析に既存ツールがどこまで効くか

- **道具**: AProVE、NaTT、KoAT2、CoFloCo（全て導入済み・未使用）
- **なぜ噛むか**: 可逆言語のループ（`from-until`）は**逆向きにも決定的**という特殊構造を持つ。
  「この構造が停止性解析を易しくするのか、むしろ既存手法の想定外なのか」は**測れば分かる**。
- **初日の実験**: Janus の `from-until` を TRS/整数遷移系に落とし、AProVE と KoAT2 に投げる。
  YES/NO/TIMEOUT の分布を出す。
- **層**: 層3（実測）。CeTA を通せば個々の結果に証明書が付く。
- **既知性リスク**: 中。ただし**「効かなかった」も報告価値がある**（今日の holonomic の 0/15 と同型）。

## 8. 可逆プログラムの超最適化（最小プログラムの合成）

- **道具**: CP-SAT / cvc5 SyGuS
- **なぜ噛むか**: 「この置換を計算する最小の可逆プログラム」は合成問題。
  今日の候補8（最小プログラムサイズ）を、枚挙を自作せずソルバに投げる形に変える。
  上界側なので検証器で担保できる。
- **初日の実験**: 3 ビットの置換 8! 個のうち代表を選び、CP-SAT で最小サイズを出す。
  手書きプログラムと比較。
- **層**: 層3。下界（最小性）を主張するなら SAT+DRAT が要る。
- **既知性リスク**: 中〜高。可逆回路の超最適化は既知（Golubitsky–Maslov）。
  **言語レベル（制御構造つき）なら空白の可能性。**

## 9. 静的解析の健全性を Lean で（ガベージフリー性の型システム）

- **道具**: Lean 4 + Mathlib
- **なぜ噛むか**: 「この解析を通ったプログラムはガベージを残さない」は全称命題。
  今日の実測で**既存実装はガベージを残していた**（clean でなかった）ことが分かったので、
  **それを静的に保証する仕組みには実需がある**。
- **初日の実験**: 最小の可逆言語に「終端でメモ表が空」を保証する型付け規則を与え、
  健全性（型付け ⟹ ガベージフリー）を Lean で証明する。
- **層**: **層1 が狙える。**
- **既知性リスク**: 中。可逆言語の型システムは研究があるので**本文確認が必須**。

## 10. 可逆プログラムから量子回路への写像の資源最適性

- **道具**: CP-SAT / SAT+DRAT、`proj/newlang`（Q-Intent）
- **なぜ噛むか**: 可逆プログラムを量子回路に落とすときのアンシラ数・T-count は
  **小さい核なら厳密最適が出る**（今日の候補7 と同型）。しかも下界に DRAT 証明書を付けられる。
- **初日の実験**: 3〜4 ビットの算術核を Q-Intent で回路化し、CP-SAT で最小 T-count を出す。
  既知の最適値（Golubitsky–Maslov 等）と照合して実装の妥当性を確認する。
- **層**: 層3。下界は SAT+DRAT で層3 の中でも強い形にできる。
- **既知性リスク**: 高。量子回路合成の最適化は競争が激しい。**差分は「言語から降りてくる」点のみ。**

| 順 | 案 | 道具の噛み | 新規性 | 既存資産 | 層1 が狙えるか |

**推奨は 4 → 2 の 2 本立て。**

- **4（資源アトラス）が最も確実。** 今日の計測基盤がそのまま使え、
  「可逆プログラムの資源を横断実測した文献が無い」という空白が明確で、
  しかも**各点に厳密最適の基準線を添えられるのは我々だけ**（CP-SAT/BFS の資産）。
  定理が要らないので層の問題も起きない。
- **2（逆化の Lean 証明）は層1 を増やす唯一級の案。** 今日分かったとおり
  **層1 は Lean でしか取れず、現状 2 定理しかない**。ここを増やすことは
  プロジェクト全体の主張の質を上げる。
- **5（ガベージ最小化パス）は 4 と 2 が進んでから。** 今日の定理 A を実装に落とす仕事で、
  4 の測定基盤と 2 の正しさの保証が揃ってからのほうが安全。

**避けるべき順序**: 10 と 8 を先にやること。既知性リスクが最も高く、
今日 4 件を既知に降格させた経験からすると、**先に本文確認で潰れる可能性が高い**。
