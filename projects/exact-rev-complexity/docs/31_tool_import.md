# 31 — 成熟した外部ツールを輸入する（2026-07-27）

`docs/30_cross_field.md` は「分野」の結合を扱う。本稿は**道具**の輸入を扱う。
きっかけは候補3 で判明した方針の反転（我々が ML に与えるのではなく、
ML の MILP 定式化を我々が輸入すべき）。同じ構図が他の道具にもある。

## 0. なぜこの分野で道具の輸入が特に効くのか

**探索は難しいが検証は自明**という非対称性がある。

- スケジュールが最適かを決めるのは指数時間（BFS の状態爆発、PSPACE 完全性）。
- しかし**与えられたスケジュールが規則を守るかの検証は線形時間**（`verify_schedule` が既に実装済み）。
- したがって**当てにならない道具（LLM・RL・ヒューリスティクス）を安全に使える**:
  出力を検証器に通せばよく、間違った出力は捨てるだけ。**信頼は不要。**

この非対称性がある限り、「賢いが保証のない探索器」＋「愚直だが確実な検証器」の組み合わせが
常に正しい設計になる。**下界側は非対称性が逆（存在しないことの証明が必要）なので、
そこは SAT の証明ログや定理証明器が要る。** 以下、上界側と下界側を分けて並べる。

## 1. QBF ソルバ × Dymond–Tompa ゲーム 【新規性 高・道具の適合が最も正確】

### なぜ効くか

**Chan 2013**: 可逆ペブル数は **Dymond–Tompa ゲーム**・Raz–McKenzie ゲームと**同値**
（`docs/20_prior_art.md` §3）。これらは**2人ゲーム**である。

- 1人ゲーム（普通のペブリング）を SAT に載せるのは自然だが、
  **2人ゲームの自然な符号化は QBF（量化ブール式）** である。
- QBF ソルバはこの10年で大きく成熟した（CAQE, DepQBF, Quabs 等、QBFEVAL の継続）。
- **つまり「可逆ペブル数を QBF で計算する」は道具と問題が正確に噛み合う。**

### 空白の可能性

Meuli 等は**可逆ペブリングを直接 SAT** で解いている（時間展開＋充足可能性）。
これは 1 人ゲームとしての符号化である。**Dymond–Tompa 側から QBF で攻めた例は
（要一次確認だが）見当たらない。** 同値性は 2013 年に知られているのに、
計算側でそれを使った例が無いなら、そこが空白。

### 最初の実験

1. Dymond–Tompa ゲームの規則を確認し（Chan 2013 の本文）、QBF に符号化する。
2. **我々の BFS の厳密値（$n\le7$ の全 DAG、木、ピラミッド）と一致するかを検証**。
   一致すれば符号化が正しい。**一致しなければ符号化か同値性の理解が誤り。**
3. 一致したら、BFS が届かない範囲（$T_7$ の $M^*$、$n=8,9$ の DAG）へ。

### リスク

QBF ソルバの実力は問題依存で振れが大きい。小域で BFS に負けるなら早期撤退。
外部ソルバの導入が必要（**ユーザー確認要**）。

## 2. FunSearch 型の LLM ループ 【新規性 高・検証器があるので安全】

### なぜ効くか

FunSearch（Romera-Paredes et al., Nature 2024）は
「**構成を出力するプログラム**を LLM に書かせ、高速な評価器で採点し、良いものを残して進化させる」
枠組みで、cap set 問題の新しい下界構成を見つけた。**成立条件は「評価器が速いこと」**で、
我々はそれを持っている（スケジュール検証器＋厳密値との比較）。

### 我々に効く使い方は2つある

- **(a) 上界側: スケジュール構成の発見。**
  「DAG を受け取ってスケジュールを返す関数」を LLM に書かせ、
  手数を採点関数にする。既知の族（Bennett 再帰、k-ratic、飽和直線スイープ）を
  **上回る構成が見つかれば、それは新しい上界定理の候補**になる。
  厳密最適が分かっている小域で「最適に届くか」を測れるので、**進捗が定量的に見える**。
- **(b) 下界側: ポテンシャル関数の発見。**
  下界証明の核は「1手で高々 $c$ しか変化しない量 $\Phi$」を見つけることで、
  これは**関数の探索**である。LLM に $\Phi$ の候補を書かせ、
  **全数データで単調性を検査**し、通ったものだけ人間（と Lean）が証明する。
  予想 A の下界（候補3 の最重要課題）がまさにこの形。

### 最初の実験

- (b) から始める。予想 A の下界のためのポテンシャル候補を機械的に列挙・検査する枠組みを作る
  （LLM を使わずに、まず「ペブル数・最右位置・区間数の線形結合」等の
  パラメトリックな族を全数検査するだけでも効く可能性がある）。
- **LLM は最後に足す。** 自前の族で済むならそれが本プロジェクトの流儀
  （`docs/00_overview.md` の「効いた手」参照）。

## 3. AlphaZero 型の RL × 大きな DAG のスケジューリング 【実用価値 高・両分野に出せる】

### なぜ効くか

可逆ペブリングは**文字通りゲーム**（状態・手・目標がある）。AlphaZero 系の
「self-play ＋ MCTS ＋ 価値/方針ネットワーク」はこの形に直接適用できる。しかも:

- **我々の厳密値が学習の検証データになる**（$n\le7$ の全 DAG、fib $n\le49$ 等）。
  「学習した方針は小域で最適に何%届くか」を厳密に測れる。**これは我々のデータの正しい使い道**
  （ML への ground truth 提供という当初の見立ては `docs/30_cross_field.md` §1 で訂正済みだが、
  **自分たちの学習器の検証用**という用途は残っている）。
- 出力は**必ず検証器に通す**ので、学習器が嘘をついても害がない。
- 実用側の需要が明確（量子回路のアンシラ管理、ML の再計算、可逆コンパイラ `rcc`）。

### 最初の実験

1. 小域（$n\le16$ の鎖、fib 型）で MCTS のみ（学習なし）を試す。
   **厳密値に届く割合**を測る。届かないなら方針ネットワークを足す価値がある。
2. 学習ありに進むなら、依存の導入（PyTorch 等）が必要 → **ユーザー確認要**。
   `~/dev/github.com/tetsuo-jp/pytorch-revnet` 等の既存資産あり。

### リスク

「RL で組合せ最適化」は論文が多く、**新規性は手法ではなく対象と検証の厳密さ**に置く必要がある。
「厳密最適が分かっている領域で学習器を検証した」という点を売りにする。

## 4. SAT/MaxSAT ＋ 証明ログ（VeriPB / DRAT）【下界側の本命】

### なぜ効くか

我々の下界は現在「全数探索したから」でしか支えられていない。
SAT コミュニティは**探索に機械検証可能な証明ログを吐かせる**技術を成熟させた
（DRAT、そして擬ブール制約向けの **VeriPB**）。**VeriPB の開発者は Nordström のグループ**
＝可逆ペブリングの複雑性を研究している当人たちなので、話が通じる。

### やること

「ピーク $p$ で $M$ 手未満は不可能」を擬ブール制約として符号化し、
UNSAT の証明ログを取得して検証器にかける。得られれば
**「探索したから正しい」→「証明を添えた」**に格上げできる。

### 空白の可能性

Meuli 等の SAT 利用は**上界（充足解＝スケジュール）**を得るためのもの。
**下界に証明ログを付けた例は見当たらない**（要一次確認）。

## 5. Lean 4: 表ではなく**探索アルゴリズムを1回だけ**認証する 【レバレッジ最大】

### 現状の弱点

いま Lean は「$n\le N$ の表が正しい」を `native_decide` で検証する使い方しかしていない。
これは表が増えるたびに検証が要り、`native_decide` は信頼境界も広い。

### 転換

**BFS そのものの正しさを1回証明する。**
「この関数は clean 到達可能な最小手数を返す」を Lean で証明してしまえば、
**以後すべての表がその定理の帰結として自動的に認証される。**

- 必要なもの: 状態空間の有限性、BFS の正しさ（最短距離を返す）、モデルの形式化。
  Mathlib には有限グラフと最短路の素材がある。
- さらに **Aut 商が最短距離を保つ**という我々の補題（候補1）も形式化対象として面白い
  （群作用と不変性の議論なので Mathlib と相性が良い）。
- 近年の Lean は自動化（`aesop`、`duper`）と LLM 支援証明で**作業量が大きく下がっている**。

### 論文になる形

ITP/CPP/JAR のツール枠。「可逆ペブリングの厳密値を出す**認証付き**エンジン」。
候補5（可逆 BB）の全数検査もこの枠組みに載る。

## 8. 第2陣（追加提案）— 摩擦が低く効果が大きいもの

### 8.1 OR-Tools **CP-SAT** 【今日試せる・最有力の「まず入れる道具」】

Google OR-Tools の CP-SAT は SAT・CP・MILP のハイブリッドで、**無償・pip 一発・Python API**、
しかも**最適性を証明して停止する**。§30 で決めた「ML の MILP 定式化を輸入する」計画は、
Gurobi のような商用ソルバ抜きでこれで実行できる。

- $M^*(G,p,e)$ を時間展開の CP モデルとして書き、`AddBoolOr`／`AddAtMostOne` と
  区間変数で組む（MOCCASIN の retention interval の発想を流用）。
- **検証**: 小域で BFS の厳密値と一致するか。一致すれば大 DAG へ。
- 副産物: 最適解が出るだけでなく、**探索が尽きたこと（＝下界）も CP-SAT が保証**する。

### 8.2 **ZDD（Zero-suppressed BDD）による記号的 BFS** 【状態空間が集合族なので原理的に噛み合う】

我々の状態は**頂点部分集合**であり、探索中に扱うのは**部分集合の族**である。
**ZDD は「集合族を圧縮して表現する」ために作られたデータ構造**（Minato、Knuth TAOCP 4A）。

- 明示的な `dict[int,int]` の代わりに、各距離レベルの状態集合を ZDD で持ち、
  「1手で到達できる集合族」を ZDD 演算で一括計算する（記号的 BFS）。
- ペブル上限 $p$ は「濃度が $p$ 以下の集合族」という ZDD の得意な制約。
- 期待: 状態数が $10^7$ を超える領域で桁違いに効く可能性。$T_7$ の $M^*$ が射程に入る。
- 実装: CUDD / Sylvan / `graphillion`（Python から ZDD を扱える）。
  **Knuth の資料が使えるのは先行プロジェクト（TAOCP 関連ノート）と相性が良い。**

### 8.3 **IC3 / PDR による帰納的不変量の自動生成** 【§2 の手作業を機械が代替する】

「ピーク $p$ では到達不能」は**到達不可能性**の主張であり、
IC3/PDR（nuXmv、ABC）は**それを証明する帰納的不変量を自動的に構成する**。

**これは §2 で人手（と LLM）で探そうとしている「ポテンシャル関数」そのものである。**
つまり §2 の前に §8.3 を試すべき可能性がある。得られた不変量は人間が読んで
一般 $n$ の証明に育てられる（機械が見つけた不変量を人間が一般化する、という分業）。

### 8.4 **clingo（Answer Set Programming）** 【符号化の試作が最速】

SAT の符号化を手で書くより、ASP なら規則をほぼそのまま書ける（`clingo` は成熟・無償）。
`#minimize` で最適化もできる。**新しいモデル（$e$ 予算・スタック領域つき）を試作する段階では
CP-SAT より速く書ける。**当たりを見つけたら CP-SAT や SAT に移す。

### 8.5 **Alloy / TLA+ によるモデル検査** 【候補4 の対応定理を安く検証する】

PRO 論文の背骨である**対応定理**（ガベージフリー実行 ⟺ clean スケジュール）は、
小さいインスタンスで**全数反例探索**すれば安く検証できる。Alloy（有限モデル発見）や
TLA+ / Apalache はこれ専用の道具である。定理を書く前に「反例が無いこと」を確認できる。

### 8.6 **性質ベーステスト（Hypothesis）** 【トレース↔スケジュール変換の検証】

候補4 の実験 A（実装のトレースを正規化する）は変換のバグが致命的になる。
ランダム生成した実行に対して「正規化 → 検証器が通る」を性質として書けば、
バグを早期に潰せる。自前の乱択テストでも足りる。

### 8.7 **Soufflé（Datalog）** 【実プログラムからメモ依存 DAG を抽出する】

候補4 の実験 D（実プログラムの DAG を取る）は静的解析である。
依存関係の抽出は Datalog が得意で、Soufflé は成熟している。
ただし対象が Janus/R-WHILE の小さな言語なら自前で書くほうが速い可能性が高い。

### 8.8 見送るもの（理由つき）

- **Sage / ore_algebra**: holonomic は自前実装で足り、しかも結果は「存在しない」だった
  （`data/holonomic_findings.md`）。導入の価値なし。
- **LODA**（OEIS 数列を生成するプログラムの探索）: 面白いが、我々の数列は min-plus 起源で
  短いプログラムに落ちる見込みが薄い。安いので気が向いたら。
- **商用ソルバ（Gurobi 等）**: CP-SAT で足りるなら不要。

## 10. 「成熟性」で並べ替える（§9 は新規性順、本節は成熟性順）

新規性で選ぶと未成熟な道具に賭けることになる。**成熟性を第一基準にすると順位が変わる。**

### 10.1 成熟性の操作的な基準

| 基準 | 意味 |
|---|---|
| **年数と継続性** | 20年以上、いまも active に開発されているか |
| **競技による淘汰** | SAT Competition / MiniZinc Challenge / QBFEVAL / CASC 等で毎年殴り合っているか |
| **産業での大規模実運用** | EDA・物流・スケジューリング等で実際に金が動いているか |
| **エコシステム** | Python API・文書・例が揃い、**学生が1週間で使えるか** |
| **失敗の安全性** | **間違った答えを静かに返さないか**（証明ログ・型検査で担保されているか） |

**最後の基準が最も重要。** 成熟した道具の本質は「速い」ことではなく
**「嘘をつかない」**ことである。

### 10.2 成熟性ランキング

| 階層 | 道具 | 成熟の根拠 |
|---|---|---|
| **A: 最も成熟** | **SAT（CDCL: Kissat, CaDiCaL）** | 30年・毎年競技・**DRAT 証明ログが競技で必須化**＝信頼性の担保まで成熟。UNSAT は証明付きで返る |
| **A** | **OR-Tools CP-SAT** | Google 内で大規模実運用・MiniZinc Challenge 常勝・**Python API と文書が最良**・最適性を証明して停止 |
| **A** | **nauty / Traces** | 40年・グラフ同型の事実上の標準。**既に導入済み**（未使用） |

### 10.3 成熟性を第一基準にした推奨

**1位: OR-Tools CP-SAT。** A 級のうち**エコシステムが最良**で、我々の用途（最適化＋最適性証明）に
そのまま合う。学生に振れるのも大きい（Python・文書・例が豊富）。

**2位: SAT + 証明ログ（Kissat/CaDiCaL + DRAT）。** 最も成熟した道具。
**下界に証明を付けられる唯一の実用的な道具**なので、我々の弱点（「全数探索したから正しい」）を
直接治す。CP-SAT が最適性を出せない規模でも、SAT なら「$M$ 手未満は UNSAT」を証明できる。

**3位: nauty。** **既に入っていて使っていない。** 候補2 の $n=8,9$ がこれで開く。
新規性はゼロだが、成熟性と即効性では最上位。

**4位: ZDD。** 状態が集合族という構造的な一致があり、基盤技術としての成熟度も高い。

**逆に、成熟性を基準にすると QBF（§1）と LLM/RL（§2, §3）は後回しになる。**
QBF は「道具と問題の適合」は最良だが「道具の成熟度」は中位——
**適合の良さと成熟性が食い違う例**であり、だからこそ #5 と #1 で順位が入れ替わる。

### 10.4 使い分けの原則（本節の結論）

> **上界側（構成を見つける）は未成熟な道具でよい。検証器があるので嘘が排除できる。**
> **下界側（存在しないことを示す）は成熟した道具が必須。証明ログか定理証明器を使う。**

この原則に従うと、道具の配置はこうなる:

- 上界: CP-SAT → 足りなければ RL/LLM（検証器で担保）
- 下界: SAT+DRAT / IC3-PDR の不変量 / Lean での一般証明
- 前処理・列挙: nauty、ZDD
- 試作: clingo
