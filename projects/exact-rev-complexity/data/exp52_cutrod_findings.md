## 2. 最大の発見: **ガベージは消えていない。メモ表からスタックへ移っただけ**

`topDownCutRod` は**メモ表が終端で空**（clean）だが、**スタックのピークが 75,802**。
一方、`_symmetric`（コメントに "An inefficient solution ... (local B-method)" とある版）は
**スタックが 39** しか要らないが、**メモ表を dirty のまま残す**。

$$\text{topDownCutRod: メモ } 7,\ \text{スタック } 75{,}802
\qquad\text{vs}\qquad
\text{\_symmetric: メモ } 10,\ \text{スタック } 39$$

**「clean だから空間効率が良い」わけではない。** `topDownCutRod` の総空間は
$7 + 75{,}802$ で、`_symmetric` の $10 + 39$ より**3 桁大きい**。
`uncall` による逆計算で**メモ表は片付くが、その過程の分岐履歴がスタックに積まれる**。

→ これは `data/exp03_results.md` §D.2 の 3 資源の整理を**実測で裏づける**:

| 操作 | 買うもの | 実測での現れ方 |
|---|---|---|
| スタックへ push | **空間で時間を買う** | `topDownCutRod` のスタック 75,802 |
| clean な逆計算（`uncall`） | **時間で空間を買う** | `topDownCutRod` の総歩数 8,497（`_symmetric` の 8.9 倍） |
| 不可逆消去 | 熱で時間を買う | **実装にはこの選択肢が無い** ← 本稿の第 3 の設計点 |

**3 つ目の通貨（熱）を実装は一切使っていない。** これが本稿の主張の位置である。

## 3. `twoMemoTables` は「ペブルを増やして手数を減らす」設計だが実測では逆

コメントは "An efficient solution for the rod cutting problem with two memo tables" だが:

- メモ peak が **20**（表 2 枚 × 10）で `topDownCutRod` の 7 の約 3 倍
- 総歩数は **27,157** で `topDownCutRod` の 8,497 の **3.2 倍**

**空間も時間も増えている。** ただし断定は避ける:
`main` が呼ぶ回数・呼び方が 3 本で異なる可能性があり、**同一の計算量で比較していない**。
公正な比較には `exp51` と同様に**入力と呼び出し回数を揃えた縮小版**が必要（§5）。

## 4. §9 に書ける文（更新版）

`exp51` §7.3 で得た「実装は最適スケジュールの put 部分だけを実行している」に加えて:

> **実装が持つ選択肢は 2 つだけである。** メモ表を clean にする代わりに
> $\Theta(\text{大})$ のスタックを積む（`topDownCutRod`: メモ 7・スタック 75,802）か、
> スタックを小さく保つ代わりにメモ表を dirty のまま残す（`_symmetric`: メモ 10・スタック 39）。
> **どちらも熱（不可逆消去）を使っていない。**
> 本稿の第 3 の設計点は、$\Theta(\sqrt n)$ ビットの消去を許すことで
> **メモも clean・スタックも不要・時間も線形**を同時に達成する。

これは **3 資源すべてが実測値で埋まった**表になるので、§9 が「提言」から
「既存 2 設計の実測と、それを支配する第 3 の設計の提示」に格上げされる。
