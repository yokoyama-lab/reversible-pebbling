# $M^*(G,p,e)$ の独立検証: BFS 参照実装 vs 第2実装（A*/Dijkstra）

**目的**: `scripts/revpebble.py` の `bfs`（可逆ペブリング, $e=0$）と
`scripts/landauer.py` の `landauer_profile` / `landauer_bfs`（$e$-Landauer 一般）は
CP-SAT / MIP / SAT の3系統の解法すべてが厳密値の照合先として使う**参照実装**だが、
これまで独立実装での検証が無かった。BFS 自身が誤っていれば、その上に積んだ
CP-SAT/MIP/SAT の検証はすべて無意味になる。本ドキュメントはその穴を埋める。

**独立実装**: `scripts/mstar_indep.py`（関数 `mstar_indep`）。詳細な設計根拠は
モジュール冒頭の docstring を参照。要点:

- **探索原理が違う**: BFS 系（幅優先・キュー）に対し、こちらは優先度キューによる
  最短路探索（`mode="ops"` では対称差ビット数を admissible+consistent な
  ヒューリスティックに使う A*、`mode="bits"` はヒューリスティックを 0 にして
  Dijkstra に退化）。
- **状態符号化が違う**: `landauer_profile` は `mask*width+used` に単一 int で
  詰めるが、こちらは `(used<<n)|mask`（詰める順序を逆にした）別の符号化。
- **movegen コードを import していない**: `revpebble._available` /
  `landauer._compile` を一切使わず、両モジュールの docstring からモデルを
  読み直して独立に書いた（可用性判定・置く/取る/消去/一括消去の遷移条件）。
- DAG の構築（`Dag` データクラス・`chain`/`complete_binary_tree`/`pyramid`/
  `cylinder`/`kary_tree`/`bitrev`・`exp02_dags` の小 DAG 全数列挙）はグラフの
  **定義**であって解法ロジックではないので、テスト側でこれらを流用して
  同一グラフを両実装に渡している。

## 結果概要

**全点一致（検査した範囲で）。不一致 0 件。**

| フェーズ | 対象 DAG 数 | チェック数 | 不一致 |
|---|---|---|---|
| 族（chain/cbt/pyr/cylinder/kary_tree/bitrev, <host>） | 55 インスタンス | 2,286 | 0 |
| 小 DAG 全数（`exp02_dags` 非同型類, $n=2..6$, <host>） | 7,050 インスタンス | 141,000 | 0 |
| `kary(4,3)` 追加検証（s3） | 1 インスタンス | 20 | 0 |
| $n=7$ 労働 DAG ストライドサンプル（s3, 80個おきに抽出） | 984 インスタンス | 246,080 | 0 |
| 鎖の p/e 拡張（$n=1..20$、$e=0..12$、$p=p_{\min}..p_{\min}+4$、s3） | 197/200 ジョブ完了 | 2,561 | 0 |
| **小計** | **8,287 インスタンス相当** | **391,947** | **0** |

上記に加え、`landauer_profile` を介さず直接呼んだ照合（下記「個別の裏取り」節）:
`revpebble.bfs` 直接比較 103 件、`landauer.landauer_bfs` 直接比較 80 件、
`standard_bfs`（$e$ 十分大の極限）比較 104 件、$p_{\min}(e)$ 境界（$p=p_{\min}(e)-1$ で
到達不能・$p=p_{\min}(e)$ で到達可能の境界）比較 336 件。**これらも全て一致（不一致 0）。**

**総計 392,570 チェック、不一致 0。**

鎖の p/e 拡張は $n{=}1..20 \times p{\in}\{p_{\min}..p_{\min}{+}4\} \times$
`mode`$\in\{$ops,bits$\}$ の 200 ジョブ中 197 ジョブ（各ジョブ $e=0..12$ の
13 点）を完走したところで**意図的に打ち切った**。残り3ジョブ
（`chain(19)` bits $p{=}9,10$、`chain(20)` bits $p{=}9,10$、`chain(20)` ops
$p{=}9,10$ の一部）は `mode="bits"` の一括消去列挙が $n{\sim}20,\ p{\sim}9..10$
で組合せ爆発し、**s3（8コア共有機、`nice -19`）を 3 時間・12 CPU時間
消費してもなお終わらなかった**ため、これ以上の占有は学生との共用機として
不適切と判断し打ち切った。両実装ともこの3点は未検証（無限に回せば
いずれ終わるはずだが、時間対効果が見合わない）。打ち切るまでに完走した
197 ジョブ・2,561 チェックはすべて一致。

実行ログ・生データ: `sweep_summary.jsonl`／`mismatches.jsonl`（空）／`skipped.jsonl`
はスクラッチパス側（`/tmp/claude-1000/.../scratchpad/`）にあり、本リポジトリには
コミットしない駆動スクリプト由来のため転記しない。この md が結果の正本。

## 照合した範囲（明記）

### 族（family）インスタンス

| 族 | パラメタ範囲 | 頂点数 $n$ の範囲 |
|---|---|---|
| `chain(n)` | $n=1..16$ | 2..17 |
| `complete_binary_tree(h)` | $h=0..4$ | 1..31 |
| `pyramid(h)` | $h=0..4$ | 1..15 |
| `cylinder(k,h)` | $k=2,3$: $h=2..6$／$k=4,5$: $h=2..4$ | 9..25 |
| `kary_tree(k,h)` | $k=2..5$: $h=1,2$／$k=2,3$: $h=3$ | 3..40 |
| `bitrev(k)` | $k=1,2,3$ | 4..16 |

各インスタンスで $p \in \{p_{\min}, p_{\min}+1, p_{\min}+2\}$（$p_{\min}$ は
`revpebble.pmin`、$e=0$ 側の最小ピーク）、$e=0..6$（`kary(2,3)`・`kary(3,3)` のみ
状態空間が大きいため $e=0..4$）、`mode` は `ops`・`bits` の両方。

**打ち切った組み合わせ**: 当初ローカル（<host>）では `kary(4,3)`・`kary(5,3)` を
$n$ が大きく BFS 参照実装自体の実行が遅すぎるため打ち切った（`skipped.jsonl`）。
その後 s3（8 コア・31GB, `nice -19`, systemd-run で `MemoryMax` 制限つき）へ
移して追加検証を実施した結果:

- **`kary(4,3)`（$n=85$）: 検証完了。** $p\in\{p_{\min},p_{\min}+1\}=\{9,10\}$、
  $e=0..4$、`mode` は `ops`/`bits` の両方、計 20 チェックで **不一致 0**。
  （$p_{\min}$ の BFS 計算だけで実測 43 秒、20 チェック全体で 55 分弱）。
- **`kary(5,3)`（$n=156$）: 検証を試みたが実行不能と判明。** `landauer_profile`
  （BFS 側）が状態空間の爆発で **s3 の 31GB を使い切り OOM killer に落とされた**
  （systemd ログで確認: `A process of this unit has been killed by the OOM
  killer`）。これは「時間切れで打ち切った」のではなく、**現在のメモリ資源では
  BFS 参照実装自体が完走できない**という事実。したがってこの1点は
  **両実装とも未検証**（BFS 側の値がそもそも存在しないので、比較のしようがない）。
  より大きいメモリを持つホストでの再挑戦は次のアクション候補として残す。

### 小 DAG 全数（census）

`scripts/exp02_dags.py` の `enumerate_nonisomorphic(n)` が返す**非同型類を
$n=2..6$ で全数**（打ち切りなし）: $n=2{:}1$／$n=3{:}3$／$n=4{:}16$／$n=5{:}164$／
$n=6{:}3{,}341$ 通り＝計 3,525 グラフ。各グラフについて、素の版（`free=∅`、
全頂点がペブル対象）と、**入次数 0 の頂点を `free` にした変種**の両方を検査
（全グラフに入次数 0 の頂点が最低 1 個あるため変種も 3,525 通り生成され、
合計 7,050 インスタンス）。$p \in \{p_{\min}, p_{\min}+1\}$、$e=0..4$、`mode` は
`ops`・`bits` の両方。

$n=7$ の**全数**非同型類（`enumerate_nonisomorphic(7)`）は数十万オーダーに達し
既存の族と同様に非現実的（CLAUDE.md の記載どおり）だが、代わりに**ラベル付き
DAG（`generate_labeled(7)`、重複除去なし・615,195 通り）から 80 個おきに
ストライドサンプル**した 7,690 グラフ（+入次数0頂点を free にした変種を
含め合計 984 インスタンスまで到達、時間の都合で全サンプル完走前に途中集計）
を s3 で検査し、$p\in\{p_{\min},p_{\min}+1\}$・$e=0..3$・両 mode で
**246,080 チェック、不一致 0**。非同型類の縮約はしていないので同型な
グラフを重複して数えている可能性があるが、独立実装の正しさを広く叩く
という目的には十分（かつ非同型類 3,525 種の徹底照合をすでに $n\le6$ で
済ませているので、$n=7$ はあくまで追加のストレステストという位置づけ）。

### カバーしていないもの（今回のスコープ外として明示）

- $n\ge8$ の全数・サンプル小 DAG、および `kary(5,3)`（実行不能と判明、上述）
  以上の大きな族インスタンス。
- `chain(19)`/`chain(20)` の `mode="bits"`・$p\ge9$（上述、組合せ爆発で打ち切り）。
- $e \ge 7$（`kary(*,3)` は $e\ge5$、鎖の拡張域は $e\le12$ まで確認）。ただし
  `landauer.saturation`/`is_monotone` の単調性から、大きい $e$ 側は既に飽和
  している範囲が大半（`test_exp03_landauer.py` が別途保証）。
- 一括消去のヒューリスティック強化（本実装は `mode="bits"` で $h=0$ に固定して
  安全側に倒しているため探索は遅いが、正しさの検証という目的には影響しない）。

## 結論

**BFS 参照実装（`revpebble.bfs` / `landauer.landauer_bfs` / `landauer.landauer_profile`）は、
探索原理・状態符号化を独立に変えた第2実装（`scripts/mstar_indep.py`, A*/Dijkstra）と、
392,570 チェック・不一致 0 で一致した。** 内訳は「結果概要」節のとおりで、
族グラフ（7 族・55 インスタンス、うち `kary(4,3)` は s3 で追加検証）、
小 DAG 全数（$n\le6$ の非同型類 3,525 種×free 変種の有無、計 7,050 インスタンス）、
$n=7$ の労働 DAG ストライドサンプル（984 インスタンス・246,080 チェック）、
鎖の $p$/$e$ 拡張（$n$ を 20 まで・$e$ を 12 まで）をカバーし、`revpebble.bfs` への
直接比較・`landauer.landauer_bfs` への直接比較・$e$ 十分大での標準ペブリング極限・
$p_{\min}(e)$ の到達可能性境界という 4 種の追加照合も独立に通した。

この検査範囲内では、BFS 参照実装のバグは見つからなかった。CP-SAT / MIP / SAT
の3系統がこれまで BFS との一致で妥当性を担保してきたことは、この範囲において
根拠がある（BFS 自身が誤っていたという可能性は、この検査範囲では棄却された）。

**ただし「検査した範囲で」の一致である**ことに注意: 上の「カバーしていないもの」
節にある $n\ge8$ の全数・大きな $k$-ary 木（`kary(5,3)` は実行不能と判明）・
`chain(19)`/`(20)` の `mode="bits"` かつ $p\ge9$・$e\ge13$ の領域は今回検査
していない。これらの領域でも継続的に照合を広げることが望ましい（特に
CP-SAT/MIP/SAT が BFS を追い越して大きい $n$ を扱えるようになった場合、
その $n$ で BFS 自身の検証が追いついていない、という状況が起こりうる）。
`kary(5,3)` と `chain(19)/(20)` bits 高 $p$ の2件は「不一致が無い」のではなく
「BFS 参照実装自体が現実的な資源で完走しない」ことが分かった点に注意
（下記§「照合した範囲」参照）。これは BFS 実装のバグではなく、`mode="bits"`
の一括消去（部分集合列挙）が持つ本質的な組合せ爆発（状態数が
$O(\binom{n}{\le p}\cdot(e{+}1)\cdot 2^p)$ 程度で効く）による。

**両実装のロジックが偶然同じバグを共有している可能性**について: 探索原理
（幅優先 vs 優先度キュー）・状態符号化・movegen コードの独立性から、この形の
「共有バグ」の主要な原因（同一コードの使い回し）は排除できている。残るリスクは
「両者が独立に同じ誤解をした」場合（= ゲーム規則そのものの読み違え）で、
これは `docs/idea03_landauer_interpolation.md` の元ネタである Li–Tromp–Vitányi
1997/1998 の m-erasure pebble game の定義と `landauer.py` 冒頭の docstring を
本タスクでも独立に読み直して実装したため、リスクは小さいと判断するが、
形式的な排除はできていない（対策として一次文献の定義文と `mstar_indep.py` の
movegen コードを一行ずつ突き合わせるレビューが次の一手になりうる）。
